# Loan EMI Tracker (Python backend)

A full-stack web app for tracking staff/member loans — add members, issue
loans, auto-generate a reducing-balance EMI schedule, monitor outstanding
balances, foreclose loans early, and view a member-wise outstanding report.

**Stack:** React (Vite) frontend + **Python (FastAPI)** backend, in-memory
data store.

> This is the Python backend rewrite of the original Node/Express version,
> done to match a Python-developer role. Logic, endpoints, and behaviour are
> identical — only the implementation language changed.

---

## Features

- **Staff login** (mock/hardcoded credentials)
- **Member management** — add members with name, member code, monthly salary
- **Loan issuance** — principal + tenure, fixed 8% p.a. reducing balance
- **Auto-generated EMI schedule** — EMI/interest/principal/outstanding per
  month, reduces to exactly ₹0 on the last row
- **Loan detail view** with full schedule
- **Member-wise outstanding report**
- **CSV export** of the report (frontend-side)
- **Indian currency formatting** (`₹1,23,456`)
- **Bonus: Foreclosure** — outstanding principal + current month's interest
- **Bonus: Top-up gating** — blocks a 2nd active loan until the first is
  ≥33% repaid
- **Bonus: Automated tests** for the EMI engine (pytest)

## Getting started

You need **Python 3.10+** and **Node.js 18+** installed.

### 1. Backend (FastAPI)

```bash
cd backend
python3 -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
python main.py
```

Backend runs at **http://localhost:4000**. On startup it seeds 3 demo
members and 2 demo loans (in-memory, resets on restart).

Interactive API docs (auto-generated by FastAPI) are available at
**http://localhost:4000/docs**.

### 2. Frontend (unchanged)

New terminal:

```bash
cd frontend
npm install
npm run dev
```

Frontend runs at **http://localhost:5173** and calls the backend at
`http://localhost:4000/api` — no changes needed here since the API
contract (paths, request/response shapes) is identical to the original
Node version.

> Both servers must be running at the same time.

## EMI calculation logic

Reducing-balance method — interest each month is charged only on the
outstanding balance, not the original principal, so the EMI amount stays
constant while the interest/principal split shifts every month.

```
EMI = P × r × (1+r)^n / ((1+r)^n − 1)
```
`r` = monthly rate (8% p.a. ÷ 12), `n` = tenure in months.

The final month's row force-clears any rounding drift (Python's `round()`
uses banker's rounding, same as the original's need to reconcile drift) so
the balance always lands on exactly ₹0. See `backend/emi.py` for the full
reasoning in comments.

## Why Python / FastAPI for the backend

The original submission used Node/Express (allowed by the brief: "Node/
Express, FastAPI, or similar — use whatever you're fastest and most
confident in"). This version rebuilds the backend in **Python with
FastAPI** to better match a Python-developer role — same logic, same
endpoints, same tests, just idiomatic Python instead of JS.

FastAPI (not Django) was chosen because:
- It matches the assignment's own suggested list.
- It's lightweight and async-friendly, appropriate for this small scope.
- It uses **Pydantic models** for request validation, which is a clean,
  type-safe equivalent to the manual validation the Express version did
  by hand.
- Django's ORM is built around a real database; this app deliberately
  uses in-memory storage (allowed by the brief), which fits better with
  a minimal framework than with Django's DB-centric design.

---

## Tech choices and why

- **FastAPI** — modern, fast, minimal boilerplate; built-in request
  validation via Pydantic; auto-generated interactive docs at `/docs`.
- **In-memory store** (`store.py`) — plain Python dicts/lists, seeded with
  3 demo members and 2 demo loans. No SQLite/Postgres — the brief
  explicitly allows this, and it keeps setup to `pip install && python
  main.py` with zero DB config. Data resets on restart.
- **Frontend unchanged (React + Vite)** — the assignment doesn't restrict
  the frontend's language, and the API contract didn't change, so the
  existing frontend works against this backend with zero modifications.
- **Auth** — hardcoded single staff account, checked by the backend, token
  stored in `localStorage` on the frontend. No real session management —
  matches "mock/hardcoded login is fine" in the brief.

## Assumptions made

1. **"Outstanding balance" without a repayment-tracking flow** — no "mark
   EMI paid" action exists; outstanding = full principal until foreclosed.
   The schedule table shows how the balance *would* reduce if EMIs are
   paid on schedule.
2. **Due dates** = loan creation date + N months (calendar-month
   arithmetic, day clamped to the target month's last valid day).
3. **Rounding** — Python's `round()` uses banker's rounding (round-half-
   to-even), same as most languages' default; whole rupees only, final
   row absorbs drift.
4. **Foreclosure** = outstanding principal + one month's interest on that
   amount.
5. **Top-up gating** reuses the "repaid so far" schedule logic — a row
   counts as repaid once its due date has passed; blocks a 2nd active loan
   until the first is ≥33% repaid.
